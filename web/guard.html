emem-guard

A verdict server for AI checkpoints. It reads a transcript, checks the emem citations in it, and answers allow or deny with a signed, logged, machine-readable reason.

01What it does

A checkpoint pauses a request and asks an external server whether to proceed. emem-guard is that server for claims about the physical world.

Content scanners (DLP) look for card numbers, secrets and classified markings. They hold no observations of the world, so they cannot check whether a stated elevation or NDVI is right. emem-guard checks that part, and accepts other detectors as plug-in modules.

  1. Find every emem: token in the transcript.
  2. Resolve each one against the responder it is pointed at. A bad signature, or a token that resolves to other bytes, is a denial.
  3. Allow a token this node has never seen. It cannot be told apart from one minted by another responder.
  4. Sign the verdict and append it to a hash-chained log, then answer.

02Run it

The steps below follow SKILL.md. The terminal output was captured from a node started in an empty directory; only line wrapping was changed.

Test before you trust it

The suite includes the two webhook-signature mistakes the platform documentation lists as most common: hashing a re-encoded body, and decoding the secret with the URL-safe base64 alphabet. Both are pinned by tests.

terminal, your own nodesh
$ cargo test --release -p emem-guard
test result: ok. ... 0 failed

Ask for a verdict

POST /verdict, your own nodesh
$ curl -sS -X POST localhost:8080/verdict \
    -H 'content-type: application/json' \
    -d '{"texts":["Elevation there is 918 m per emem:fact:defi.zb493.xuqA.zcb5f:abc123"]}'

{ "action": "allow", "leaf": "leaf_0", "checked": 1 }

checked is the number of citations examined. An allow with checked: 1 and an allow with checked: 0 are different statements.

Failure semantics

For an Inference hook, a non-200 response, a timeout or an unparseable body is not a deny. The organisation's failure policy decides, and under fail-open the prompt goes to the model unchecked. Sustained failures trip a circuit breaker.

So every input gets a 200 and a verdict: an unknown event type, a malformed body, an empty body.

terminal, your own nodesh
$ curl -sS -w "\nHTTP %{http_code}\n" -X POST localhost:8080/verdict/anthropic-hook \
    -H 'content-type: application/json' \
    -d '{"type":"some_event_type_that_does_not_exist_yet","request_id":"probe"}'

{"action":"allow"}

03Claim gating

The other rules deny when a check fails. claim_gating denies when no check was offered: a sentence states a measurable quantity about a place or time, and the transcript cites nothing.

Because it denies on absence, it ships off. Shadow mode runs every rule, signs and logs what it would have done, and blocks nothing, so you can measure the rate on your own traffic before enforcing it.

terminal, your own nodesh
$ ./target/release/emem-guard --claim-gating --shadow --data ./var/guard
  mode     shadow: every rule runs and is logged, nothing is blocked.
           read it back with emem-guard --report --data ./var/guard
  claims   on: a measurable claim with no citation is denied.

With a citation that resolves

POST /verdict, your own nodejson
{"texts":["Canopy height in Sumatra reached 31 m on 2026-08-05,
           per emem:fact:defi.zb521.jawI.gOze:f3yr3urkrfwamlemwadulgth2qpw645vi6l6fhtuu4dy5o7onahq."]}

{ "action": "allow", "leaf": "leaf_3", "checked": 1 }

The rule checks that the citation resolves. It does not check that the citation is about the claim: the fact cited here is Lusail's elevation. Relevance is still the reader's job.

With a citation that does not resolve

Change four characters of the cid and the denial stands. Since 2026-08-08, grounding means resolved; before that, any token-shaped string cleared the rule.

POST /verdict, your own nodejson
{"texts":["Canopy height in Sumatra reached 31 m on 2026-08-05,
           per emem:fact:defi.zb521.jawI.gOze:f3yr3urkrfwamlemwadulgth2qpw645vi6l6fhtuu4dy5o7o22hq."]}

{
  "action": "deny",
  "reason": "EMEM-GUARD DENY CLAIM_UNGROUNDED token=- fix=cite_observation leaf=leaf_7",
  "code": "CLAIM_UNGROUNDED",
  "fix": "cite_observation",
  "checked": 1
}

No PROV_ code fires on the unresolved token: a token from another responder is legitimate. CLAIM_UNGROUNDED says only that nothing cited grounds the sentence on this node.

What counts as a claim

A sentence fires only if its unit appears in a table where every row names the band that reports it: metres from copdem30m.elevation_mean, mm/day from weather.precipitation_mm, µg/m³ from cams.pm25. Bytes, seconds, hertz and currency have no band, so 800 ms never fires.

Three more conditions must all hold. The sentence has a world anchor (an ISO date, a year, a coordinate pair, or a preposition before a capitalised name). It is an assertion, not a question, hedge or conditional. It is prose, not code or configuration.

POST /verdict, your own nodejson
{"texts":["The verdict path took 800 ms and the transcript limit is 10 MB."]}

{ "action": "allow", "leaf": "leaf_4", "checked": 0 }

Over this repository's own documentation the rule fired 3 times in 8,739 sentences across 8 files (0.034%). Two were its own positive test fixtures; one was a changelog line stating a rainfall rate on a date with no citation.

04Wrong value, real citation

A citation can resolve, verify and name the right cell while the number written beside it differs from the number inside it.

Example: a memo stated an NDVI of 0.62 next to the genuine token for a fact that reads 0.138. The signature, the receipt and the inclusion proof all checked out.

POST /v1/guard/verdict, emem.devjson
{"texts":["Peak-season NDVI at Dindori was 0.62 in 2025,
           per emem:fact:defi.zb4e4.zcced.fUrI:3u37m4qb...yg6oq."]}

{
  "action": "deny",
  "reason": "EMEM-GUARD DENY PROV_VALUE token=emem:fact:defi.zb4e4.zcced.fUrI:3u37m4qb...yg6oq fix=correct_value leaf=-",
  "code": "PROV_VALUE",
  "fix": "correct_value",
  "checked": 1,
  "citations_found": 1
}
CodeFires when
PROV_SIGthe signature does not verify
PROV_BYTESthe token resolves to different bytes
PROV_DRIFTthe value moved past a threshold
PROV_VALUEthe sentence states a different value than the fact it cites
CLAIM_UNGROUNDEDa measurable claim cites nothing that resolves

The fix is correct_value: keep the citation, change the number. Three conditions keep the rule from flagging honest text.

  1. A value this node read. A node with no corpus never reaches the rule.
  2. One citation per sentence. With two, the rule would have to guess which number goes with which citation, so it does not fire.
  3. Your precision. 889.6439208984375 written as 889.6 m passes; 5000 m does not.

A citation right after the sentence it supports also counts, as in "sits at 5000 m elevation. [emem:fact:…]".

Not checked: relevance. A token that resolves is not proof it is about the place the sentence names. A real Nashik reading cited beside a claim about Bengaluru is allowed.

05Checkpoints

One engine, nine request shapes. Seven are open formats with more than one implementation; two are vendor hooks.

RouteCalled byOpenHosted on emem.dev
POST /verdictany agent or framework; the native shape (alias /verdict/native)yesyes
POST /verdict/mcpan MCP host or proxy, gating a tool call or a tool resultyesyes
POST /verdict/openaianything with an OpenAI-shaped clientyesyes
POST /verdict/cloudeventCloudEvents 1.0 producers: Knative, Dapr, Argo Eventsyesyes
POST /verdict/policyOPA-style clients, Envoy external authorisationyesyes
POST /verdict/batchan offline scan of many transcripts, up to 64 per callyesyes
GET /log/entry/{leaf}anyone checking a verdict without trusting the nodeyesno: emem.dev keeps no verdict log
POST /verdict/anthropic-hookclaude.ai, Cowork and Claude Code in a Claude Enterprise orgnono: needs your organisation's signing secret
POST /verdict/claude-codeagents on the Platform API, Bedrock and Vertex, which Inference hooks do not seenono: runs inside your agent

A test asserts that every advertised route answers and that open routes outnumber vendor routes.

MCP

Put a proxy between an MCP host and its servers, and ask before dispatching a tool call.

POST /verdict/mcp, your own nodejson
{"jsonrpc":"2.0","id":7,"method":"tools/call",
 "params":{"name":"read_file","arguments":{"path":"notes.md"}}}

{ "allow": true, "id": 7,
  "verdict": { "action": "allow", "leaf": "leaf_1", "checked": 0 } }

On a deny the response carries result, already shaped as a CallToolResult with isError set. Return it in place of running the tool, and the model reads the denial and the fix where it reads tool errors.

Send params.result in place of params.arguments to check a tool's output as it enters the context, one turn before the model reasons on it.

06The verdict log

Every verdict is signed and appended to the log before the caller gets an answer. A denial names the leaf that records it.

GET /log/entry/leaf_0, your own nodejson
{
  "seq": 0,
  "record": {
    "checkpoint": "emem.native.v1",
    "request_id": "01KZAWCH25KXHYHAJHWK03151D",
    "outcome": "allow",
    "evaluated": "allow",
    "mode": "enforce",
    "checked": 1,
    "decided_at_unix_s": 1785997968
  },
  "signature_b32": "p4cfqpvlyymax6wg5lrshfn2t7tt6stw73saprg3oi57pvdbl7gri...",
  "signer_b32": "zwkuk6ahc6qseltbq7expaz2omd2vjkqjhv5criovu53sqy7qmwa",
  "chain": "7a99eac5a05dac1a8b0e16ee9867d1daa03ac3aa55ff72ab77d10086abfd816f"
}

An entry holds the record, the signature over its preimage, the signing key and the link to the previous entry. outcome and evaluated are both signed, so an operator cannot later relabel a shadow verdict as enforced.

Audit the chain

Signatures prove each entry. The chain proves none was removed. An intact log exits 0.

terminal, your own nodesh
$ emem-guard --audit --data ./var/guard
entries        5
bad signature  []
broken chain   []
unparseable    []
intact         true
$ echo $?
0

Edit one logged verdict from allow to deny and the audit exits 1, so a scheduled audit fails its pipeline.

terminal, your own nodesh
$ emem-guard --audit --data ./var/guard
entries        5
bad signature  [0]
broken chain   [0]
unparseable    []
intact         false
$ echo $?
1

Deleting a line leaves every remaining signature valid; the chain breaks at the gap. GET /log/head publishes the head for a witness to pin, and GET /log/entries?start=0 lets anyone mirror the log.

07Try it here

emem.dev runs the same engine in advisory mode. It is in nobody's request path and blocks nothing; it tells you what a guard would answer.

POST /v1/guard/verdict, live on this originlive
Press the button. The response comes from emem.dev, not from this page.

A token this responder does not hold returns allow. Denying it would penalise an agent for citing another node.

The same routes, from a shell

The six hosted verdict routes accept the same bodies as a self-hosted node, so only the host changes.

runs against emem.dev as printedsh
curl -sS -X POST https://emem.dev/verdict \
  -H 'content-type: application/json' \
  -d '{"texts":["Elevation there is 918 m."]}'

# an MCP tools/call, gated
curl -sS -X POST https://emem.dev/verdict/mcp \
  -H 'content-type: application/json' \
  -d '{"method":"tools/call","params":{"name":"read","arguments":{"q":"emem:fact:a:b"}}}'

# an OpenAI-shaped body, and an OPA-style policy input
curl -sS -X POST https://emem.dev/verdict/openai  -d '{"input":"..."}'  -H 'content-type: application/json'
curl -sS -X POST https://emem.dev/verdict/policy  -d '{"input":{"prompt":"..."}}' -H 'content-type: application/json'

# what this origin does and does not serve
curl -sS https://emem.dev/.well-known/emem-guard.json

emem.dev keeps no verdict log, so /log/entry returns a typed refusal. Each hosted verdict carries an Ed25519 receipt instead, which /verify checks.

Run your own

A self-hosted node generates its own signing key and keeps its own log. It asks the responder one question, whether a fact cid resolves, under a timeout inside the verdict budget.

terminal, your own nodesh
$ curl -s https://emem.dev/v1/guard/selfhost | jq -r .skill > SKILL.md
$ git clone https://github.com/Vortx-AI/emem && cd emem
$ cargo build --release -p emem-guard
$ ./target/release/emem-guard --responder https://emem.dev

Over MCP the same two entry points are tools: emem_guard_verdict to get a verdict, emem_guard_selfhost to get the procedure.

08Design decisions

Three choices that could have gone the other way.

DecisionReason
A token this node has not cached is never a denial.A self-hosted node holds a subset of any corpus, and the verdict path does not fetch. From inside the node, an uncached token and a forged one look the same.
Every uncertain case allows, including a bad signature on an inbound webhook.A non-200 is a webhook failure, which under fail-open sends the prompt through unchecked and can trip the organisation's circuit breaker. The node answers 200 with allow and logs the problem.
Claim gating ships off.It denies on absence. The detector, its four conditions, the unit table and the corpus measurement are public, and shadow mode lets you measure it on your own traffic first.

If one of these is wrong, say so on the channel. Findings are reproduced, fixed with a named test, and recorded.
