emem-guard

A signed yes/no server for claims about the physical world. Input: a transcript. Output: allow or deny, signed, logged, with a machine-readable reason. Nothing else.

This page is the self-host skill being run. Every terminal block below is real output from a node started from a clean directory, in order, with nothing edited but the wrapping.

Watch it run Check your own text → Get the skill →

No account. No API key. No network to emem.dev. cargo build --release -p emem-guard and it runs.

01The half nobody built

A checkpoint holds a request and asks an external server whether to proceed. The named destinations for that question all evaluate content: does this text contain a card number, a secret, a classified marking. None of them can evaluate whether a claim about the world is still true, because none of them hold signed observations of it.

emem-guard evaluates the other thing. It finds the emem: citations in a transcript, resolves each one, and answers on the evidence. A cited observation whose signature fails is a denial. A cited observation this node has never seen is not, because that is indistinguishable from one minted by another responder.

The verdict is signed and appended to a hash-chained log before it is returned. Requests to a security server are already signed on the way in; verdicts come back as unsigned JSON into a mutable database, so nobody can later prove what was allowed, denied, or why. A compliance API that reports its own history is testimony. An append-only log with a chain is evidence.

It is not a DLP scanner

Detection accuracy is a race against vendors with hundreds of engineers maintaining thousands of patterns, and winning it would grow nothing that matters here. emem-guard is the chassis those engines run on: physical-world verification native, everyone else's detection pluggable, every verdict provable.

Step 5 — ask it something

The native route. No vendor envelope, no account, no installed client.

POST /verdict — your own nodesh
$ curl -sS -X POST localhost:8080/verdict \
    -H 'content-type: application/json' \
    -d '{"texts":["Elevation there is 918 m per emem:fact:defi.zb493.xuqA.zcb5f:abc123"]}'

{ "action": "allow", "leaf": "leaf_0", "checked": 1 }

checked: 1 is doing work. An allow that examined one citation is a different statement from an allow that examined none, and a caller deserves to tell them apart.

Step 6 — the failure semantics most integrations get wrong

A webhook failure is not a deny. A non-200, a timeout or an unparseable body hands the decision to the organisation's failure policy, and under fail-open the prompt reaches the model uninspected. Sustained failures trip a circuit breaker that stops enforcement for everyone.

terminal — your own nodesh
$ curl -sS -w "\nHTTP %{http_code}\n" -X POST localhost:8080/verdict/anthropic-hook \
    -H 'content-type: application/json' \
    -d '{"type":"some_event_type_that_does_not_exist_yet","request_id":"probe"}'

{"action":"allow"}
HTTP 200

An event type it has never seen still gets a verdict. So does a malformed body, an empty body, and JSON of the wrong shape. There is no error path.

03The rule that fires on absence

Every other rule denies on a check that failed. claim_gating denies on a check that was never offered: a sentence asserting a measurable quantity about a place or a time, in a transcript that cites nothing at all. That is a much stronger thing to say about someone's prompt.

So it ships off, and it ships with the instrument that makes turning it on a decision rather than a guess. Shadow mode runs every rule, signs and logs what it would have done, and blocks nobody.

terminal — your own nodesh
$ ./target/release/emem-guard --claim-gating --shadow --data ./var/guard
  mode     shadow: every rule runs and is logged, nothing is blocked.
           read it back with emem-guard --report --data ./var/guard
  claims   on: a measurable claim with no citation is denied.

Send it a draft that cites nothing:

POST /verdict — your own nodejson
{"texts":["Canopy height in Sumatra reached 31 m on 2026-08-05."]}

{
  "action": "allow",
  "reason": "EMEM-GUARD DENY CLAIM_UNGROUNDED token=- fix=cite_observation leaf=leaf_2",
  "code": "CLAIM_UNGROUNDED",
  "fix": "cite_observation",
  "leaf": "leaf_2",
  "shadowed": true,
  "claim": {
    "sentence": "Canopy height in Sumatra reached 31 m on 2026-08-05.",
    "magnitude": "31 m",
    "quantity": "length",
    "source_band": "copdem30m.elevation_mean",
    "anchor": "iso_date"
  }
}

action: allow, because nobody is being blocked. shadowed: true, because the rule fired. And source_band: "copdem30m.elevation_mean", which is the actionable part: it names where a citable observation would come from, so the remedy is resolve elevation there and cite it rather than cite something.

That field has to name a band POST /v1/recall will actually serve. Until 2026-08-08 it named dem, a family root from GET /v1/bands that recall answers with unknown_band, so every pointer the gate emitted sent the agent somewhere that does not exist. Where no band reports a quantity at all, hectares and cubic metres among them, it is now null: the claim is still ungrounded, and this node is saying it cannot ground it either, which is more useful than a confident wrong answer.

Add a citation that resolves and the rule declines:

POST /verdict — your own nodejson
{"texts":["Canopy height in Sumatra reached 31 m on 2026-08-05,
           per emem:fact:defi.zb493.xuqA.zcb5f:yqbolgeoycqkvj3zkxukb4bjw4odhpwvfzqo3fbgwf4spk45zala."]}

{ "action": "allow", "leaf": "leaf_3", "checked": 1 }

A citation that does not resolve buys nothing. Change four characters of that cid and the denial stands:

POST /verdict — your own nodejson
{"texts":["Canopy height in Sumatra reached 31 m on 2026-08-05,
           per emem:fact:defi.zb493.xuqA.zcb5f:yqbolgeoycqkvj3zkxukb4bjw4odhpwvfzqo3fbgwf4spk45za22."]}

{
  "action": "deny",
  "reason": "EMEM-GUARD DENY CLAIM_UNGROUNDED token=- fix=cite_observation leaf=leaf_7",
  "code": "CLAIM_UNGROUNDED",
  "fix": "cite_observation",
  "checked": 1
}

This is the 2026-08-08 correction, and it mattered more than it looks. The rule used to decline the moment any token was present, resolved or not, so pasting a plausible-looking string turned a denial into an allow while the receipt's fact_cids stayed empty. Defeating the gate cost less than satisfying it, which is the worst property a control can have. Grounding now means resolved.

Note what did not change: an unresolvable citation is still never a provenance denial. No PROV_ code fires on it, because a token minted by another responder is legitimate and, from inside this node, indistinguishable from a forgery. CLAIM_UNGROUNDED is a narrower and true statement: nothing you cited grounds this sentence here.

When the citation is real and the sentence still lies

A citation can resolve, verify, and bind to the right cell while the number written beside it is not the number inside it. Two desks running a lending simulation found this independently: a memo asserting an NDVI of 0.62, carrying the genuine token for the fact that reads 0.138. Right cell, right band, right observation. Every provenance check passed, the receipt arithmetic balanced, and the inclusion proof was valid.

POST /v1/guard/verdict — emem.devjson
{"texts":["Peak-season NDVI at Dindori was 0.62 in 2025,
           per emem:fact:defi.zb4e4.zcced.fUrI:3u37m4qb...yg6oq."]}

{
  "action": "deny",
  "reason": "EMEM-GUARD DENY PROV_VALUE token=emem:fact:defi.zb4e4.zcced.fUrI:3u37m4qb...yg6oq fix=correct_value leaf=-",
  "code": "PROV_VALUE",
  "fix": "correct_value",
  "checked": 1,
  "citations_found": 1
}

No older code could express this. PROV_SIG is a bad signature, PROV_BYTES is a token resolving to other bytes, PROV_DRIFT is a threshold, and CLAIM_UNGROUNDED is a claim with no citation at all. None of them means the sentence disagrees with the fact it cites. That was missing from the design rather than from the implementation, and PROV_VALUE is the answer to it.

The fix is correct_value, never drop the citation. The citation is the sound half; the prose is what disagrees with it.

Three things keep the rule from denying honest writing. It needs a value this node actually read, so a node with no corpus never reaches it. It needs exactly one citation in the sentence, because deciding which figure answers which citation is the same guess the claim gate refuses to make. And agreement is judged at the precision you wrote: reporting 889.6439208984375 as 889.6 m is correct, while 5000 m is not. Calling ordinary rounding a lie would make the rule unusable.

A citation that trails the sentence it supports still counts. “sits at 5000 m elevation. [emem:fact:…]” is the ordinary way to cite, and a rule that only looked inside one sentence missed every memo written that way.

What it still does not check is relevance. A token that resolves is not evidence that it is a token about the place the sentence names. Cite a real Nashik reading beside a claim about Bengaluru and this allows.

And ordinary engineering prose never reaches it at all:

POST /verdict — your own nodejson
{"texts":["The verdict path took 800 ms and the transcript limit is 10 MB."]}

{ "action": "allow", "leaf": "leaf_4", "checked": 0 }

Why 800 ms is not a claim about the world

The discriminator is a unit table where every row names the band that reports it. Metres come from copdem30m.elevation_mean, millimetres per day from weather.precipitation_mm, micrograms per cubic metre from cams.pm25, all of them keys recall will serve rather than the family roots they sit under. Bytes, seconds, hertz and currency are absent because no band reports them, so a claim measured in one is not a claim this node could have verified had it been cited. The gate is bounded by its own competence.

Three more clauses have to hold, and each can only ever remove firings: a world anchor (an ISO date, a year, a coordinate pair in range, or a preposition followed by a capitalised name), an assertion rather than a question, a hedge, a conditional or an already-attributed statement, and prose rather than a fenced code block or a configuration line.

Measured over this repository's own documentation, the register the gate will sit in front of: 3 firings in 8739 sentences across 8 files, a rate of 0.034%. Two of the three are the detector firing on its own positive test fixtures, sentences written to be gateable claims, so they are the rule working rather than false positives; the third is a changelog line that genuinely asserts a rainfall rate on a date and cites nothing. They are counted apart rather than excluded, because hiding them would flatter the number.

The corpus found two real defects on the way, both now fixed and pinned by tests: a citation key (Reiche-2018) and a model name (gpt-4o-2024) each read as a year.

04Nine checkpoints, seven of which belong to nobody

A checkpoint is any system that pauses before doing something and asks an external server whether to proceed. A gate reachable only through one company's product is a gate for that company's customers, so most of these are standards with more than one implementation behind them and no owner who can revoke them.

RouteReachesOpenRuns on emem.dev
POST /verdictany agent, on any model, through any framework. The native shape.yesyes
POST /verdict/mcpany MCP host or proxy, gating a tool call or a tool resultyesyes
POST /verdict/openaianything holding an OpenAI-shaped clientyesyes
POST /verdict/cloudeventCloudEvents 1.0 producers: Knative, Dapr, Argo Eventsyesyes
POST /verdict/policyOPA-compatible clients, Envoy external authorisationyesyes
POST /verdict/batchmany transcripts at once, for scanning an archive offlineyesyes
GET /log/entry/{leaf}anyone checking a verdict without trusting the node that issued ityesno: emem.dev keeps no verdict log
POST /verdict/anthropic-hookclaude.ai, Cowork and Claude Code inside a Claude Enterprise orgnono: needs your org secret
POST /verdict/claude-codeagents on the Platform API, Bedrock and Vertex, which Inference hooks cannot seenono: runs inside your agent

A test asserts every route the node advertises actually answers, and that the open ones outnumber the vendor ones. That is a commitment the build checks, not a posture in a README.

Six of them also run right here. emem.dev hosts the vendor-neutral verdict routes over the same engine, advisory and blocking nothing, so a client you developed against a local node can be pointed at this origin without changing anything but the host. The three it cannot serve say why rather than 404: the two vendor hooks need your organisation's own secret and your own request path, and /log/entry needs a verdict log, which an advisory responder does not keep and will not pretend to. /.well-known/emem-guard.json lists exactly which is which.

The MCP one is the most portable

MCP is an open protocol with many independent hosts. Put a proxy between a host and its servers and ask before dispatching.

POST /verdict/mcp — your own nodejson
{"jsonrpc":"2.0","id":7,"method":"tools/call",
 "params":{"name":"read_file","arguments":{"path":"notes.md"}}}

{ "allow": true, "id": 7,
  "verdict": { "action": "allow", "leaf": "leaf_1", "checked": 0 } }

On a deny the response carries result, already shaped as a CallToolResult with isError set. Return it instead of running the tool and the model sees the denial and the remedy where it already reads errors. The proxy never has to learn the reason grammar.

It gates the other direction too, which is the one most systems miss. Send params.result instead of params.arguments and a fabricated citation is caught as it enters the context, rather than a turn later once the model has reasoned on it.

A reason line ending in leaf=leaf_2 is a promise. Here is the mechanism behind it.

{
  "seq": 0,
  "record": {
    "checkpoint": "emem.native.v1",
    "request_id": "01KZAWCH25KXHYHAJHWK03151D",
    "outcome": "allow",
    "evaluated": "allow",
    "mode": "enforce",
    "checked": 1,
    "decided_at_unix_s": 1785997968
  },
  "signature_b32": "p4cfqpvlyymax6wg5lrshfn2t7tt6stw73saprg3oi57pvdbl7gri...",
  "signer_b32": "zwkuk6ahc6qseltbq7expaz2omd2vjkqjhv5criovu53sqy7qmwa",
  "chain": "7a99eac5a05dac1a8b0e16ee9867d1daa03ac3aa55ff72ab77d10086abfd816f"
}

The record, the signature over its preimage, the key that signed, and the link to the entry before. Verifying it involves nothing from the node that served it. outcome and evaluated are both in the preimage, which is what makes a shadow report evidence: an operator who could relabel one as the other afterwards could claim enforcement they never ran.

Signatures prove each verdict. The chain proves none were removed.

$ emem-guard --audit --data ./var/guard

$ echo $?

Now flip one logged verdict from allow to deny, exactly as someone hiding a decision would:

terminal — your own nodesh
$ emem-guard --audit --data ./var/guard
entries        5
bad signature  [0]
broken chain   [0]
unparseable    []
intact         false
$ echo $?
1

A non-zero exit, so a scheduled audit fails a pipeline rather than printing a problem nobody reads. Delete a line instead of editing one and every remaining signature still verifies, which is exactly why the chain is there: it breaks at the seam.

GET /log/head publishes the head so a witness or a mirror can pin it. GET /log/entries?start=0 lets anyone mirror the whole log without the node's cooperation.

06Check some text against this responder

The same engine, hosted here and advisory: this responder is not in anybody's request path and nothing below blocks anything. It answers what a guard would say, so you can see the thing before you build anything.

POST /v1/guard/verdict — live, this originlive
Press the button. The response is generated by this node, not by this page.

Paste a token that does not resolve here and you get allow, not deny. That is the design: a citation this responder has not cached is indistinguishable from one minted by another responder, and denying on it would punish an agent for citing across nodes, which is the behaviour the token format exists to enable.

Advisory here: this origin is in nobody's request path and blocks nothing. It keeps no verdict log either, so /log/entry answers a typed refusal naming why rather than a 404, and each hosted verdict carries an ed25519 receipt instead, verifiable at /verify.

Then run your own

A node you run needs no account here and no key from us. It generates its own signing key, keeps its own log, verifies what it holds, and cites what it does not. Ask it for the procedure and it hands you one written to be executed unattended.

terminal — your own nodesh
$ curl -s https://emem.dev/v1/guard/selfhost | jq -r .skill > SKILL.md
$ git clone https://github.com/Vortx-AI/emem && cd emem
$ cargo build --release -p emem-guard
$ ./target/release/emem-guard --responder https://emem.dev

Your verdicts stay yours: signed with your key, written to your log, never leaving your machine. The responder is asked one thing, whether a fact cid resolves, under a hard timeout the verdict deadline cannot exceed.

From MCP, the same two doors are tools: emem_guard_verdict to consult, emem_guard_selfhost to build.

07Three judgement calls worth arguing with

These are choices, not consequences. Each one could be made the other way, and each would produce a different product.

A token this node has not cached is never a denial

It is indistinguishable from one minted by another responder, a self-hosted node holds a subset of any corpus by design, and the verdict path is forbidden from fetching, so cold and false cannot be told apart from inside. Denying on it is the single most likely way this product gets uninstalled.

Every uncertain case allows, including a bad signature on the inbound webhook

A non-200 is a webhook failure, not a deny. Under fail-open it sends the prompt to the model uninspected, and sustained failures trip a breaker that stops enforcement for the whole organisation. So an unverified request gets 200 with an allow and a line in the operator log. That reads wrong the first time and it is right.

Claim gating denies on absence, so it ships off behind a measurement

Not behind an opinion. The detector, its four clauses, the unit table with its per-row provenance and the corpus measurement are all in the open, and shadow mode exists so an organisation measures the trade on its own traffic before making it.

If any of the three is wrong, say so on the channel. A finding gets reproduced first, fixed with a test named, and recorded whether or not it is flattering.
