Two surfaces cannot drift because they are generated from the compiled constants the server signs against: /v1/verifier_spec (the exact preimage and canonical-order rules to re-check any receipt or authorship yourself) and the a2a block in /.well-known/mcp.json (the agent-collaboration front door). When a narrated page and one of those disagree, trust the generated one.

The whole trust chain, once, with real ids

The reference below lists endpoints. What it does not show is the chain they form, which is the thing a consuming agent actually has to assemble: read a fact, check who signed it, dereference the citation, and confirm the value you are about to publish is the value you were given. Every id here is live: paste the commands as they are. 

# 1. Read a signed fact. No key, no account.
curl -s -X POST https://emem.dev/v1/recall -H 'content-type: application/json' \
  -d '{"cell":"defi.zb572.xoso.zb1ec","bands":["indices.ndvi"]}'
#    -> facts[].value, facts[].fact_cid, and a signed receipt

# 2. Verify that receipt WITHOUT trusting this server. Offline-checkable:
#    it recomputes blake3(preimage) and the ed25519 signature.
curl -s -X POST https://emem.dev/v1/recall -H 'content-type: application/json' \
  -d '{"cell":"defi.zb572.xoso.zb1ec","bands":["indices.ndvi"]}' \
  | jq '{receipt: .receipt}' \
  | curl -s -X POST https://emem.dev/v1/verify_receipt \
      -H 'content-type: application/json' --data-binary @-
#    -> {"valid": true, ...}   (the byte rules are at /v1/verifier_spec)

# (These tokens are live facts and a responder need not hold one for ever.
#  scripts/example_check.py catches it when one stops resolving; refresh with
#  curl -s -X POST https://emem.dev/v1/recall -H 'content-type: application/json' \
#    -d '{"cell":"defi.zb572.xoso.zb1ec","bands":["indices.ndvi"]}'
#  and take any memory_token plus its value_verbatim.)
# 3. Dereference a citation someone handed you. This one is a GC-1
#    derivation: the responder RE-RAN the arithmetic, so it resolves as
#    deterministic_index rather than a claim you have to take on faith.
curl -s -X POST https://emem.dev/v1/memory_token/resolve -H 'content-type: application/json' \
  -d '{"token":"emem:fact:defi.zb572.xoso.zb1ec:4qj3l4mgh7ch5kvxmkqspjdl6y42oqhm42khh3gostccpixkbz5q"}'
#    -> the byte-identical signed fact, its provenance block, a receipt,
#       and value_verbatim: "-0.052199413489736016"  <- quote this, do not retype it

# 4. Close the last mile: confirm the value YOU are about to publish is the
#    value you were given. Rounding is caught, not forgiven.
curl -s -X POST https://emem.dev/v1/echo_verify -H 'content-type: application/json' \
  -d '{"token":"emem:fact:defi.zb572.xoso.zb1ec:4qj3l4mgh7ch5kvxmkqspjdl6y42oqhm42khh3gostccpixkbz5q",
       "claimed_value":"-0.0522"}'
#    -> {"matches": false, "drift": "rounded", ...}
#       pass the full value and it answers {"matches": true, "drift": null}

Steps 1 and 2 are emem proving its own side: these are the bytes, and this key signed them. Steps 3 and 4 are the half that used to be unguarded: a citation resolves to the same bytes for anyone, and the number you emit is checked against them. A pipeline that runs all four can state that every value it published was echo-verified, and mean it.
