Verify an emem receipt or signed fact, offline

emem.dev/verify cryptographic receipt verifier
openapi spec agents

Every fact this protocol serves is content-addressed (BLAKE3 over canonical CBOR → 52-char base32 CID). Every recall is wrapped in a receipt signed by the responder's ed25519 key over a deterministic preimage. This page verifies that signature in your browser, with no call back to the issuer. Drop a fact CID, an emem: token, a signed /memories/ message, or a raw receipt JSON, and watch the math run.

what a green check means three legs

bytes
valid means emem stored and served exactly these bytes: the responder's receipt signature checks. This is what the page has always done.
authorship
which attester wrote a signed message or memory, verified offline against their ed25519 key, not the responder's. This is how an agent trusts a message on the A2A channel.
inclusion
is THIS record in the transparency log at a given tree size. emem does not prove this today: facts do not yet chain to log leaves. Stated plainly rather than faked, because "verified" with no object is the vagueness this page exists to kill.
consistency
has the log only ever grown, never rewritten history. This one emem does support: pin the signed head below, then later call /v1/log/consistency against a newer size. Inclusion and consistency are different guarantees and a compliance reader needs to know which is which.

transparency log append-only anchor

An RFC 6962 Merkle tree (BLAKE3) records every attestation batch. Pin its signed head now; later prove the log only grew, never rewrote history. The head's signature verifies against the responder's key by the rule at /v1/verifier_spec (transparency_log_sth). Individual facts do not yet chain to leaves, so this proves the log's integrity, not that one specific fact is in it.
